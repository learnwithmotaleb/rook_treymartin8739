---
name: iOS build-number drift
description: Why a successful Expo Launch build may never appear in TestFlight, and how to keep build versions monotonic.
---

An Expo Launch workflow may successfully produce and sign an iOS build but fail when uploading to App Store Connect if Expo's remote build-number counter is behind Apple's latest accepted build. A failed upload means TestFlight remains on the old build; do not infer that the Launch wizard was never run from an unchanged TestFlight listing. Check the Launch failure log first.

**Why:** Apple rejected signed Rook IPAs with lower bundle versions than its existing TestFlight build even though the bundle ID and target App Store Connect app matched. The user also confirmed the accepted build and failed Launch appear under the same Expo account/project, so do not assume a wrong-project selection from the lower counter alone. A healthy API domain was unrelated. Changing only `ios.buildNumber` while remote versioning is enabled cannot fix this because Expo ignores the local number.

**How to apply:** Keep the build number above the latest Apple-uploaded number. Confirm the signed IPA's *actual* build number in the Launch log before claiming success. Replit's managed Launch continued to increment its remote counter after source was set to local with a higher `ios.buildNumber`; do not assume source config controls the managed workflow. Do not recommend repeated failed uploads merely to increment the remote counter one at a time. Use the supported managed-service path to sync the remote counter above Apple's latest build or correct the workflow's effective version source; if neither is exposed, the blocker is outside project code. If local versioning eventually takes effect, explicitly bump `ios.buildNumber` before later production uploads.
